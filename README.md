# AI-Driven 3D Blueprint Generator

Turn a natural-language product description into a design specification, multi-view
concept images, an interactive 3D model, an engineering blueprint and downloadable
CAD assets.

```
Text  →  Design spec  →  Multi-view images  →  3D  →  Mesh cleanup  →  CAD  →  Export
  └──── Text2Voxel-64: text straight to 3D ────┘
```

The research motivation is accessible, personalised product design: reducing the CAD
expertise needed to get from an idea — particularly a bespoke assistive device — to a
concrete, inspectable, exportable artefact.

**Live demo:** <https://puchaarunkumar.github.io/AI-driven-3D-blueprint-generator/> — a
static build on GitHub Pages. Its **Text → 3D** page runs a small text-to-3D model
(Text2Voxel-64) entirely in your browser, and the demo projects are a read-only
snapshot. Anything that needs the Python backend (image generation, reconstruction,
CAD export) is switched off there, and the site says so. See
[GitHub Pages deployment](#20-github-pages-deployment).

> **Design output, not a manufacturing drawing.** Everything this produces is a
> design-intent prototype. It carries no tolerancing scheme, no GD&T and no material
> certification, and needs engineering review before anything is fabricated.

> **Text2Voxel-64 is for non-commercial research use only.** It is trained on
> Text2Shape (ShapeNet-derived) and ModelNet40, whose terms restrict use to research,
> and the weights inherit that restriction. See
> [Licences and attribution](#25-licences-and-attribution) and the
> [model card](docs/MODEL_CARD.md).

## 1. Project overview

The application implements the documented research pipeline **Text → Image → 3D → GLB
→ BLEND** end to end:

| Stage | What actually happens |
| --- | --- |
| **Prompt analysis** | A deterministic parser extracts object, purpose, dimensions, materials, style, colour, constraints, manufacturing method, accessibility requirements and tolerances into an editable `DesignSpec`. A BERT-family encoder then **restructures** the object phrase and enriches the vocabularies by meaning, so `"a electric wheel cchair"` becomes `electric wheelchair` before it reaches the image model. |
| **Multi-view images** | One image per requested camera position, generated by a configured provider from a shared identity clause plus a deterministic per-view seed. |
| **3D reconstruction** | Silhouettes are segmented from each view, aligned so their per-axis extents agree, back-projected into a voxel grid, intersected, and surfaced with marching cubes. Vertices take colour from the view that best faces them. Learned single-image models (TripoSR, Shap-E) can be selected instead. |
| **Text-to-3D (no images)** | The alternative path. **Text2Voxel-64**, a small latent diffusion model trained for this project, turns the prompt's MiniLM sentence embedding into a coloured 64³ voxel shape, which is meshed and scaled to the prompt's dimensions. It runs in the browser on the **Text → 3D** page, or in the backend as the `text2voxel` 3D provider, where the image stage is skipped and the usual mesh, CAD and export stages follow. |
| **Mesh processing** | Vertex welding, degenerate-face removal, hole filling, Taubin smoothing, optional decimation, normal recomputation. |
| **Blueprint** | Technical line drawings projected from the mesh: **outline** (silhouette and interior contours), **inline** (crease edges) and **hidden** (occluded edges, dashed), on all three principal planes with measured dimensions. |
| **Blueprint sheet** | All three views combined on one A3 sheet in third-angle projection at a single shared scale, with dimension lines and a title block. Exported as vector SVG. |
| **CAD conversion** | Blender imports, repairs, materialises and saves a native `.blend`. FreeCAD converts the mesh to a faceted B-rep and writes STEP. |
| **Export** | GLB, glTF, OBJ, STL, PLY always; BLEND with Blender installed; STEP with FreeCAD installed. |

Every stage runs real code on real data. Where a component is unavailable on your
machine, the UI reports it and explains the remedy rather than simulating a result.

## 2. Architecture

```
React + TypeScript + Three.js (Vite)          frontend/
        │     lib/text2voxel/   text → mesh in a Web Worker (onnxruntime-web);
        │                       needs no backend
        │  REST + WebSocket job stream
        ▼
FastAPI                                       backend/app/
        │
        ├── pipeline/prompt_parser    text   → DesignSpec  (rules, then MiniLM
        │                                                    in pipeline/semantic)
        ├── pipeline/orchestrator     runs the stages, persists results
        ├── pipeline/blueprint        mesh   → line drawings; blueprint_sheet → A3 SVG
        │
        ├── providers/image/          spec   → multi-view PNGs
        │     ├── diffusers_local  (Stable Diffusion, local GPU/CPU)
        │     └── hosted           (DALL·E, Stability AI)
        │
        ├── providers/threed/         images → GLB
        │     ├── visual_hull      (multi-view silhouette carving, local)
        │     ├── triposr          (learned single-image 3D, local)
        │     ├── shap_e           (learned single-image 3D, local)
        │     ├── text2voxel       (text → GLB, local ONNX; no images needed)
        │     └── hosted           (TRELLIS/SLAT-compatible endpoint)
        │
        ├── providers/mesh/           GLB    → cleaned GLB   (trimesh)
        │
        └── providers/cad/            GLB    → BLEND / STEP
              ├── blender          (subprocess, headless)
              └── freecad          (subprocess, headless)
        │
        ▼
SQLite via SQLAlchemy (PostgreSQL-ready)  +  filesystem asset store
```

Each stage sits behind an abstract interface (`ImageGenerator`, `ThreeDGenerator`,
`MeshProcessor`, `CADExporter`) in `backend/app/providers/base.py`. Providers report
their own availability, and `ProviderRegistry` is the only thing that constructs them,
so swapping an implementation never touches the orchestrator or the UI. A
text-conditioned 3D provider (`TextTo3DGenerator`, currently only `text2voxel`) takes
the prompt instead of images, and the orchestrator skips the image stage for it.

The frontend can also run with no backend at all. The **Text → 3D** page
(`/generate`) does its whole job in the browser, and a static build
(`VITE_STATIC=true`) reads the demo projects from a pre-exported snapshot instead of
the API. That combination is the GitHub Pages site. More detail in
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

### How the 3D step works

With the default `THREED_PROVIDER=auto`, a learned model (TripoSR, then Shap-E) is
used whenever it can run; see [AI provider configuration](#10-ai-provider-configuration).
The reconstruction that is always available, because it needs nothing beyond the
base requirements, is a **visual hull** (shape-from-silhouette):

1. Segment each view into a foreground mask. A matting model (`rembg`) is used when
   available, because generated backdrops are rarely the plain white the prompt asks
   for — vignetted walls and studio floors defeat colour-based segmentation. Without
   it, a classical background-subtraction + watershed fallback runs instead.
2. Rescale the silhouettes so the object's extent along each world axis agrees between
   the views that observe it. Without this the intersection erodes to nothing, because
   independently generated images place the product at arbitrary scale and offset.
3. Back-project every silhouette through a voxel grid and combine them. With four
   or more views a voxel is kept when all but one agree, so a single bad generation
   cannot carve the model away; with fewer views the intersection stays strict.
4. Extract the surface with marching cubes; colour each vertex from the best-facing view.
5. Centre and scale to the dimensions in the specification, then write GLB.

This is a classical computer-vision method — no model weights, runs on CPU, and it
genuinely consumes the generated views. It is **not** a learned image-to-3D model, and
it cannot recover concavities no silhouette reveals. See [Limitations](#22-limitations).

## 3. Features

- Natural-language prompt → structured, **editable** design specification, with
  transformer-backed understanding that repairs typos and split words and
  recognises paraphrases ("cannot grip well" → low grip-strength operation)
- One-click multi-image upload: pick all your references at once and they fill
  Front / Rear / Left / Right / Top / Bottom / Perspective automatically
- Multi-view generation (front, rear, left, right, top, bottom, perspective) with
  per-view regeneration, deletion and reference-image upload
- Three local image-to-3D backends - silhouette carving and two learned models
  (TripoSR, Shap-E) - plus a hosted image-to-3D endpoint, all behind one interface
- Text-to-3D with no images: Text2Voxel-64, trained for this project, runs fully
  in the browser (Text → 3D page) or as the backend's `text2voxel` provider, with
  seed / guidance / step controls, GLB / STL / OBJ / PLY download and a blueprint of
  the result
- A static build of the frontend for GitHub Pages: Text → 3D plus the demo
  projects, with no server
- Viewer presentation themes: dark, studio white, noir and blueprint graph paper,
  with true edge-geometry wireframe rendering
- Interactive Three.js viewer: orbit / zoom / pan, camera reset, solid / wireframe /
  normals shading, grid, axis gizmo, bounding box, lighting and environment controls,
  fullscreen, and live model statistics
- Blueprint view: outline / inline / hidden line drawings projected from the real
  mesh on all three planes, with a hidden-line toggle, plus an isometric reference
- Combined A3 blueprint sheet in third-angle projection, downloadable as vector SVG
  in a white or classic blueprint style
- Mesh processing with a before/after report of exactly what changed
- Export manager that only offers formats the installation can actually produce
- Project persistence with full processing history, gallery and detail pages
- Real-time pipeline status over WebSocket, with polling fallback and cancellation
- Settings page reporting hardware, CUDA, provider availability and storage usage
- Demo mode: real pre-generated assets, no provider or API key needed

## 5. Text-to-3D in the browser

The **Text → 3D** page (`/generate`) turns a prompt into a coloured 3D model inside
the page itself: no backend, no GPU, no API key, and the prompt never leaves your
machine.

```
prompt → MiniLM embedding → 50 guided DDIM steps of a latent diffusion prior
       → VAE decoder → 64³ occupancy + colour → surface → mesh at your dimensions
```

What you get back:

- the model in the 3D viewer, with its statistics;
- a blueprint of it (front, side and top views with outline, inline and hidden
  lines, extracted from the voxel grid) and the combined A3 sheet as SVG, in the
  white or classic blueprint style;
- downloads as GLB, STL, OBJ or PLY;
- the model card: training data, metrics, licences and limitations.

**Controls.** *Seed*: the same seed and settings reproduce the same result in the
same browser.
*Guidance* (default 3.0): how strongly the prompt steers the sample. *Steps*
(default 50): fewer is faster and rougher. *Dimensions*: pre-filled from the prompt
with the same rules the backend parser uses (`1200 x 600 x 750 mm` is length × width
× height) and editable. The shape is scaled uniformly, never stretched: a height sets
the height; otherwise the larger of length and width sets the footprint; otherwise
the largest side is 1 m.

**What it is good at.** Text2Voxel-64 learnt free-form descriptions only for
**chairs and tables** (Text2Shape's 75k human captions). It also knows the 40
ModelNet40 categories (airplane, car, sofa, lamp, guitar, toilet, …) by name and in
12 colours, but only coarsely. At 64³ a 1 m object has voxels of about 16 mm, so thin
parts break up. It never refuses: any other prompt gets the nearest shape it knows.
The [model card](docs/MODEL_CARD.md) has the architecture, data, training and
evaluation.

**How it runs.** Everything happens in a module Web Worker using onnxruntime-web's
WebAssembly backend, so the page stays responsive. The WordPiece tokenizer, sampler,
mesher, blueprint extraction and exporters are TypeScript
(`frontend/src/lib/text2voxel/`). The WASM runtime and the model files are served
from the site's own origin, so nothing is fetched from a CDN. The first run
downloads about 70 MB - the model files, about 56 MB (decoder 8.5 MB, prior 24 MB,
MiniLM 23 MB, tokenizer 0.7 MB), plus ONNX Runtime's 14 MB WebAssembly binary - and
keeps it in the browser's Cache Storage; where that is unavailable (for example a
plain-`http` address other than `localhost`) the files are simply downloaded again.
Inference is single-threaded WASM, because GitHub Pages cannot send the headers
multi-threaded WASM needs. After the download a generation takes a second or two on
a laptop CPU, and the page reports the time of each stage.

**Running it locally.** The model files are not in git:

```bash
node frontend/scripts/fetch-models.mjs     # -> frontend/public/models/{text2voxel,minilm}/
cd frontend && npm run dev                 # open http://localhost:5173/generate
```

The page works whether or not the backend is running. `fetch-models.mjs` downloads
the files listed in `models/manifest.json`: the model from this repository's
`text2voxel-v1` GitHub release, MiniLM from Hugging Face at a pinned revision. It
verifies each file's SHA-256 when the manifest records one, skips files that are
already present and valid, and takes `--force` to download everything again or
`--check` to verify without downloading.

**The placeholder model.** Until the `text2voxel-v1` release is published there is
nothing to download. A development checkout may instead hold a placeholder: the same
architecture and file formats, trained for seconds on a few synthetic shapes, with
`"smoke": true` in its `meta.json`. The page shows a clear placeholder banner for it;
its shapes are meaningless.

The same model also runs in the backend; see
[Local text-to-3D (Text2Voxel-64)](#local-text-to-3d-text2voxel-64).

## 6. Installation

### Prerequisites

- **Python 3.11 or newer**
- **Node.js 18 or newer** (22.18 or newer for `verify-text2voxel.mjs`; the Pages workflow uses 24)
- *(optional)* **Blender 4.0+** for `.blend` export
- *(optional)* **FreeCAD 1.0+** for STEP export
- *(optional)* an **NVIDIA GPU with CUDA** for fast local image generation

### Clone and set up

```bash
git clone https://github.com/PuchaArunKumar/AI-driven-3D-blueprint-generator.git
cd AI-driven-3D-blueprint-generator
```

### Backend

Create a virtual environment. **If the repository lives inside a synced folder**
(OneDrive, Dropbox, iCloud), put the environment *outside* it — PyTorch alone is
~2.5 GB and cloud sync will thrash:

```bash
python -m venv ~/.venvs/ai3d-blueprint          # or .venv inside the repo
source ~/.venvs/ai3d-blueprint/bin/activate     # Windows: ...\Scripts\activate
```

Install PyTorch first, choosing the build that matches your hardware:

```bash
# NVIDIA GPU (CUDA 12.6)
pip install --index-url https://download.pytorch.org/whl/cu126 torch torchvision

# CPU only
pip install --index-url https://download.pytorch.org/whl/cpu torch torchvision
```

Then the rest:

```bash
pip install -r backend/requirements.txt
```

PyTorch and diffusers are optional. Without them the app still runs — local image
generation reports itself unavailable, while the demo projects, viewer, blueprint,
mesh tools and every export path keep working.

`rembg` is also optional but **recommended**: it supplies the matting model used to
separate the product from the background, which is what reconstruction quality
depends on most. Its ~176 MB model downloads on first use. If it is missing or
corrupt the backend detects that with a self-check (a blank frame must contain no
object) and silently falls back to the classical method rather than producing
garbage silhouettes.

### Frontend

```bash
cd frontend
npm install
```

### Text2Voxel model files (optional)

The text-to-3D model is not committed. Fetch it for whichever side you use:

```bash
node frontend/scripts/fetch-models.mjs          # browser:  frontend/public/models/
python backend/scripts/install_text2voxel.py    # backend:  backend/models/text2voxel/  (--force replaces)
```

Both read `models/manifest.json`, download the decoder, prior and `meta.json` from
the `text2voxel-v1` GitHub release and the MiniLM encoder from Hugging Face (about
56 MB in all), and verify SHA-256 checksums once the manifest records them. Both
target directories are gitignored. Without these files the Text → 3D page has no
model to load and the `text2voxel` provider reports itself unavailable; nothing else
is affected.

### Configuration

```bash
cp .env.example .env
```

Edit `.env` as needed. It is gitignored; **never commit it**.

## 9. GPU setup

Local image generation is dramatically faster on CUDA. Verify with:

```bash
python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
```

If `cuda_available` is `False` but you have an NVIDIA card, you installed the CPU
wheel. Reinstall from the CUDA index (see [Installation](#6-installation)).

The Settings page shows the detected GPU, VRAM, CUDA version and PyTorch build.

**One model resident at a time.** On a card with under 12 GB the backend
releases the image model's weights before loading the reconstruction model and
vice versa. Holding Stable Diffusion and TripoSR together left a 6 GB card at
~300 MB free - one request away from an out-of-memory failure. With the policy
active the same pipeline peaks at ~4.3 GB of 6.1 GB. The cost is a few seconds
to reload a model between stages; a larger GPU keeps both loaded and skips it.

**Low-VRAM notes.** The defaults target ~4 GB. On CUDA the provider requests the
model's `fp16` variant (roughly half the download and half the VRAM) and enables
attention and VAE slicing. If you still hit out-of-memory:

- lower `IMAGE_WIDTH` / `IMAGE_HEIGHT` to `384`
- keep `DIFFUSERS_MODEL=stabilityai/sd-turbo` rather than an SDXL checkpoint
- generate fewer views per run

CPU generation works but is slow — expect minutes per view rather than seconds.

## 10. AI provider configuration

### Local Stable Diffusion (default)

```bash
IMAGE_PROVIDER=diffusers
DIFFUSERS_MODEL=stabilityai/sd-turbo
```

Weights download once to the Hugging Face cache (`~/.cache/huggingface`), after which
generation is fully offline. `sd-turbo` needs 1–4 steps and no guidance. For more
detail on a larger GPU, try `stabilityai/sdxl-turbo` or
`stabilityai/stable-diffusion-2-1` (set `DIFFUSERS_STEPS=25`, `DIFFUSERS_GUIDANCE=7.5`).

### DALL·E

```bash
IMAGE_PROVIDER=openai
OPENAI_API_KEY=sk-...
OPENAI_IMAGE_MODEL=dall-e-3
```

### Stability AI

```bash
IMAGE_PROVIDER=stability
STABILITY_API_KEY=sk-...
```

### Prompt understanding

`pipeline/prompt_parser.py` extracts the specification with rules;
`pipeline/semantic.py` then refines it with **MiniLM**, a 6-layer distilled
BERT (~88 MB, CPU-fast). It does two things the rules cannot:

- **Restructures the object phrase** against a product-category vocabulary.
  This is not cosmetic: `"a electric wheel cchair"` left as-is makes a
  diffusion model draw a *car wheel*, and the pipeline then faithfully
  reconstructs a wheel. Scoring blends sentence embeddings with a
  character-level ratio, because embeddings handle split words
  ("wheel chair" -> wheelchair) while subword tokenisation handles typos badly.
- **Enriches the vocabularies by meaning**, so "cannot grip well" registers as
  a low grip-strength requirement.

It is conservative by design: a phrase that already names its head noun
("bike frame"), or that scores below threshold ("quantum flux capacitor"), is
left untouched - mislabelling a novel object is worse than leaving it alone.
Set `SEMANTIC_PROMPT=false`, or run without torch/transformers, and the rules
carry on alone.

### Local learned image-to-3D (TripoSR) - recommended

```bash
cd backend
python scripts/install_triposr.py     # fetches the source + ~1.7 GB of weights
```

```bash
THREED_PROVIDER=triposr
```

TripoSR predicts a triplane NeRF from one image in a single forward pass and
marches a mesh out of it: about **9-25 s** on a laptop GPU at ~2.5 GB VRAM, and
noticeably sharper than Shap-E. On a car it recovers the roofline, glasshouse
and wheel arches.

It is MIT-licensed but is not on PyPI and has no `setup.py`, so it is fetched
into `backend/vendor/TripoSR` (gitignored) rather than vendored. Two
compatibility layers make it run on a current environment, both in
`app/providers/threed/triposr.py`:

- its `torchmcubes` CUDA extension is replaced by scikit-image marching cubes,
  so **no build toolchain is needed**;
- the checkpoint's ViT keys are remapped from the pre-4.36 transformers layout
  (loads with zero missing and zero unexpected keys).

**Input quality dominates the result.** The model infers depth from shading, so
matte, evenly-lit subjects reconstruct well while dark glossy ones - a black car
with hard specular highlights - flatten out. If a reconstruction looks like a
slab, regenerate the views in a lighter colour before changing anything else.

### Local learned image-to-3D (Shap-E)

```bash
THREED_PROVIDER=shap_e
```

Shap-E is a generative 3D model with a prior over what objects look like, so it
recovers structure the views never showed. Weights (~1.3 GB) download on first
use; a reconstruction takes roughly 90 s on a laptop GPU at ~2.7 GB VRAM.

**Which backend to choose.** They fail in opposite directions:

| | `visual_hull` | `shap_e` |
| --- | --- | --- |
| Source | every generated view | one view |
| Faithfulness | measures the silhouettes | invents plausible structure |
| Concavities | cannot recover them | recovers them from its prior |
| Needs true elevations | **yes** - a three-quarter "front" collapses the model | no |
| Resolution | as fine as the voxel grid | modest, slightly lumpy |
| Best for | boxy, flat-sided products photographed as real elevations | vehicles and organic shapes |

For a chair or a tray the hull is sharper. For a car the hull produces a slab,
because diffusion models return three-quarter hero shots for vehicles no matter
how the prompt is worded - Shap-E is the right choice there.

Of the two learned backends, **TripoSR is the better default** - sharper and
~4x faster. Shap-E needs no extra install, so it remains the zero-setup option.

### Automatic 3D provider selection

`THREED_PROVIDER=auto`, the default, uses the first image-to-3D backend that can run
right now: TripoSR, then Shap-E, then the visual hull, which always can. `text2voxel`
is not part of that order, because with views available a reconstruction of those
views is what was asked for. `auto` falls back to it only when the project has **no
views to reconstruct from and the image provider cannot run** (no GPU model, no API
key), provided Text2Voxel is installed. A machine without an image model then still
produces a 3D model instead of failing, and the backend log records the fallback.

### Local text-to-3D (Text2Voxel-64)

```bash
python backend/scripts/install_text2voxel.py    # decoder, prior, meta.json + MiniLM, ~56 MB
```

```bash
THREED_PROVIDER=text2voxel
```

This is the same model as the browser's [Text → 3D page](#5-text-to-3d-in-the-browser),
run by onnxruntime on the CPU in
`backend/app/providers/threed/text2voxel.py`: the project's prompt is embedded with
MiniLM (tokenised by the `tokenizers` package), sampled with the same guided DDIM
sampler, decoded to 64³ occupancy and colour, surfaced with scikit-image marching
cubes, given vertex colours and written as GLB with trimesh. It is scaled uniformly
from the specification's dimensions by the same rule as the browser: height if
given, otherwise the larger of length and width, otherwise 1 m.

It needs no images, so **the full pipeline skips the Multi-view Images stage**,
showing it as skipped with the reason, then runs mesh processing, CAD conversion and
export as usual. The result records the seed, guidance, step count, occupied voxels,
stage timings, model version and whether the placeholder model was used.

It needs `onnxruntime` and `tokenizers` plus the five model files, and no PyTorch or
GPU. When anything is missing the Settings page lists it as unavailable with the
reason and the install command. `TEXT2VOXEL_STEPS` and `TEXT2VOXEL_GUIDANCE` set the
sampler; `TEXT2VOXEL_PATH` moves the model directory.

It is a generator, not a reconstruction: only the prompt text and the dimensions
reach it (not the materials or style fields, and no reference images). It is
detailed for chairs and tables and coarse for the 40 ModelNet categories, works at
64³, and carries a **non-commercial research licence**; see the
[model card](docs/MODEL_CARD.md).

### Hosted image-to-3D (experimental)

To use a learned reconstruction model instead of silhouette carving, point
`TRELLIS_ENDPOINT` at a service that accepts `multipart/form-data` with an `image`
field and returns either a binary GLB or JSON `{"model_url": …}` / `{"model_b64": …}`:

```bash
THREED_PROVIDER=trellis_api
TRELLIS_ENDPOINT=https://your-endpoint/generate
TRELLIS_API_KEY=...
```

No TRELLIS/SLAT weights are bundled — this is an integration point, not an
implementation. It is labelled *Research Component — Experimental / Optional* in the UI.

## 18. Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| *"Cannot reach the backend"* | The backend is not running, or is on another port. Start it, and set `VITE_API_TARGET` if the port is not 8000. |
| `[Errno 10048] error while attempting to bind` | Port already in use. Change `PORT` in `.env` and set `VITE_API_TARGET` to match. |
| `cuda_available: False` with an NVIDIA GPU | You installed the CPU wheel. Reinstall torch from the `cu126` index. |
| CUDA out of memory | Only one heavyweight model is kept resident below 12 GB VRAM, so this is unlikely. If it still happens, lower `IMAGE_WIDTH`/`IMAGE_HEIGHT`, drop `TRIPOSR_RESOLUTION`, or generate fewer views. The error surfaces as a readable message, not a crash. |
| Model download stalls | Delete the `*.incomplete` files under `~/.cache/huggingface/hub/models--*/blobs/` and retry; downloads resume. |
| *"No product silhouette could be separated"* | The views lack a clear object on a plain background. Install `rembg` for far better separation, regenerate the views, or upload a reference image with a clean backdrop. |
| Reconstruction looks like a slab | Segmentation is falling back to the classical method on a busy background. Check the log for "rembg self-check failed"; delete `~/.u2net/u2net.onnx` and let it re-download. |
| *"The silhouettes did not overlap"* | Views disagree wildly on scale. Regenerate, or use fewer views (front plus one side is enough). |
| `.blend` export unavailable | Blender not found. Install it or set `BLENDER_PATH`. |
| STEP export unavailable | FreeCAD not found. Install it or set `FREECAD_PATH`. |
| Blender exits with an operator error | You are on Blender 3.x. Upgrade to 4.0+, whose operator names the script targets. |
| Model does not appear in the viewer | Check the browser console. The viewer catches GLB parse failures and shows the reason in place of the canvas. |
| Slow generation on CPU | Expected. Minutes per view without CUDA. |
| Text → 3D shows a placeholder-model banner | The development placeholder (`"smoke": true`) is installed. Once the `text2voxel-v1` release exists, `node frontend/scripts/fetch-models.mjs --force` replaces it with the trained model (without `--force`, an existing file is kept while the manifest has no checksum for it). |
| Text → 3D cannot load the model | The files under `frontend/public/models/` are missing. Run `node frontend/scripts/fetch-models.mjs`. |
| `fetch-models.mjs` / `install_text2voxel.py` get a 404 | The `text2voxel-v1` release has not been published yet; see [Training Text2Voxel-64](#21-training-text2voxel-64). |
| Checksum mismatch while fetching models | The download was corrupted or the release files changed. Delete the file and retry; if the release was deliberately replaced, update `sha256` in `models/manifest.json`. |
| `text2voxel` provider unavailable | Install the requirements (`onnxruntime`, `tokenizers`) and run `python backend/scripts/install_text2voxel.py`. The Settings page names what is missing. |
| GitHub Pages: blank page, or 404 on refresh | `VITE_BASE` must be `/<repository name>/`, and `404.html` (written by `postbuild.mjs`) must be in the deployed site. |

Detailed logs, including full tracebacks, are written to `storage/logs/backend.log`.
The API only ever returns curated messages.

## 19. Deployment

Build the frontend and serve it from any static host, with `/api` and `/files` proxied
to the backend:

```bash
cd frontend && npm run build      # → frontend/dist
```

Backend behind a reverse proxy:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

Notes for a real deployment:

- **Single worker.** Jobs live in an in-process manager. To scale horizontally, move
  the job manager to Redis/Celery and share `STORAGE_DIR` across instances.
- **WebSockets.** Ensure the proxy forwards `Upgrade`/`Connection` headers for
  `/api/ws/`. The frontend degrades to polling if it cannot connect.
- **CORS.** Set `CORS_ORIGINS` to your real origin; do not leave the dev defaults.
- **Storage.** `STORAGE_DIR` must be a persistent volume — models, images and the
  SQLite database all live there.
- **PostgreSQL.** Set `DATABASE_URL=postgresql+psycopg://…`. Every column type used is
  portable; no code changes are required.
- **Secrets.** Provide them as environment variables. Never bake `.env` into an image.
- **GPU.** Container images need the NVIDIA runtime and a CUDA-matched torch wheel.

For a deployment with no backend at all, which is what the live demo is, see the next
section.

In static mode (`VITE_STATIC=true`) the API client answers read requests from a JSON
snapshot under `static-api/` and turns every write into a clear error saying the
hosted demo has no backend. Studio and Settings show an explanation instead of
failing, and the capability chip reads "In-browser".

### How a deployment happens

`.github/workflows/pages.yml` runs on every push to `main`, and on demand via
*Run workflow*:

1. Checks that Pages is enabled (`actions/configure-pages`), sets up Python 3.11 and
   installs only the backend packages the snapshot exporter needs (no PyTorch,
   diffusers or rembg).
2. Runs `backend/scripts/export_static_site.py --out frontend/public/static-api`,
   which writes the demo projects, their blueprint data and both blueprint-sheet
   styles, and copies their assets, using the real blueprint code on the committed
   demo files.
3. Runs `node frontend/scripts/fetch-models.mjs`, which downloads everything listed in
   `models/manifest.json` (decoder, prior and `meta.json` from the `text2voxel-v1`
   release, MiniLM from Hugging Face) into `frontend/public/models/`, verifying
   checksums where the manifest has them. A missing file fails the build rather than
   deploying a site without a model.
4. `npm ci`, then `npm run build` with `VITE_STATIC=true` and
   `VITE_BASE=/AI-driven-3D-blueprint-generator/` (a fork changes this to its own
   repository name).
5. `node frontend/scripts/postbuild.mjs --strict` copies `index.html` to `404.html`,
   so deep links such as `/generate` survive a refresh on GitHub Pages, writes
   `.nojekyll`, and fails the build if a model file did not make it into `dist`.
6. `actions/upload-pages-artifact` and `actions/deploy-pages` publish
   `frontend/dist`.

The model files and ONNX Runtime's WASM are served from the Pages site itself, so
the page does not depend on the release, Hugging Face or a CDN at run time. Each
visitor downloads the ~56 MB of model files and the 14 MB runtime once, which counts
against GitHub Pages' bandwidth allowance.

**One-time setup** (repository owner): set *Settings → Pages → Build and deployment →
Source* to **GitHub Actions**, and publish the `text2voxel-v1` release (see
[Training Text2Voxel-64](#21-training-text2voxel-64)). Until that release exists the
workflow fails at step 3.

## 21. Training Text2Voxel-64

The model is trained from scratch on Kaggle, not locally, by two kernels generated
from [`training/text2voxel/`](training/text2voxel/):

| Kernel | Machine | Does |
| --- | --- | --- |
| K1 `text2voxel-k1-prep` | CPU | Downloads Text2Shape (15,032 ShapeNet chairs and tables with 75,360 captions), voxelises ModelNet40 (12,311 meshes in 40 classes) at 64³, embeds every caption with MiniLM |
| K2 `text2voxel-k2-train` | 2× T4 | Trains the shape VAE (110 min) and the diffusion prior (20 min), evaluates on held-out shapes, exports ONNX (weights stored as fp16, computed in fp32) and `meta.json`, and fails if ONNX and PyTorch disagree |

```bash
python training/text2voxel/build_kernels.py
python -m kaggle kernels push -p training/text2voxel/kaggle/k1
# check K1's montages, set ORIENT in k2_train.py, rebuild, then:
python -m kaggle kernels push -p training/text2voxel/kaggle/k2
```

K2's `decoder.onnx`, `prior.onnx` and `meta.json` are published as the
`text2voxel-v1` GitHub release, their checksums go into `models/manifest.json`, and
the next push to `main` deploys them.
[`training/text2voxel/README.md`](training/text2voxel/README.md) has the full
procedure; the [model card](docs/MODEL_CARD.md) covers architecture, data, training
and evaluation.

**Status:** `text2voxel-v1` was trained on 2026-09-27 (2 x Tesla T4, 2 h 17 min).
Held-out VAE IoU is 0.824, and 91% of ModelNet category prompts produce the prompted
category. The [model card](docs/MODEL_CARD.md#evaluation) has every metric and what
it measures.

## 22. Limitations

These are real constraints of the implementation, stated plainly:

- **A visual hull cannot see concavities.** Any cavity that no silhouette reveals — a
  cup interior, a recessed housing — reconstructs as solid.
- **Multi-view consistency is approximate.** Views are independent diffusion samples
  sharing an identity clause and a seed family, not the output of a multi-view
  diffusion model. Details can drift between views.
- **Absolute scale comes from your specification, not the images.** Reconstruction
  recovers shape and proportion only.
- **Surface colour is projected from the source views**, so faces no camera observed
  are approximated from the nearest-facing view.
- **Reconstruction quality depends on background separation.** Text-to-image models
  frequently ignore "plain white background"; on a vignetted wall or a studio floor the
  classical fallback segmenter degrades badly. The matting model handles it, which is
  why `rembg` is recommended rather than merely supported.
- **STEP output is a faceted B-rep**, not a parametric solid.
- **Nothing here is a certified manufacturing drawing.**
- **TRELLIS/SLAT, NeRF and Gaussian Splatting are not implemented.** The research names
  them; this repository provides an integration point for a hosted image-to-3D model
  and nothing more. The UI marks them *Research Component — Experimental / Optional*.
  (TripoSR does build a triplane NeRF internally, but only as a step towards its mesh.)
- **Prompt understanding is rules plus a small sentence encoder.** `prompt_parser.py`
  extracts every field with rules; `semantic.py` then uses MiniLM, a distilled BERT, to
  repair the object phrase and match vocabularies by meaning. There is no fine-tuned
  or generative language model, so phrasing the rules and vocabularies do not cover
  is still missed.
- **Text2Voxel-64 is small and narrow.** It works at 64³ (about 16 mm voxels on a 1 m
  object), understands free-form descriptions only for chairs and tables, knows the
  40 ModelNet categories only coarsely and in one colour, and was not trained on any
  assistive-product category: a prompt for one of the products that motivate this
  project gets the closest thing it knows, most likely a chair or a table. It never
  refuses a prompt. See the
  [model card](docs/MODEL_CARD.md).
- **Text2Voxel-64 uses only the prompt and the dimensions.** It ignores the
  specification's materials, style and constraints, and it scales uniformly, so only
  one of three requested dimensions is met exactly.
- **Text2Voxel-64 is licensed for non-commercial research only**, because its training
  data is.
- **The hosted site has no backend.** On GitHub Pages only Text → 3D generates
  anything; the demo projects are a fixed snapshot.
- **Open3D is not a dependency** — trimesh, SciPy and scikit-image cover its role here.

The About page in the app carries this same status table, per technology.

## 23. Future work

- Replace the rule-based field extraction with a fine-tuned transformer or an
  LLM-backed structured extractor, behind the existing `parse_prompt()` interface.
  The MiniLM layer already handles the object phrase and vocabulary matching.
- Run a stronger learned 3D model (TRELLIS/SLAT) locally behind the existing
  `ThreeDGenerator` interface. TripoSR and Shap-E are integrated; TRELLIS is only
  reachable today as a hosted endpoint.
- Text2Voxel: higher resolution (sparse voxels or an implicit-surface decoder), more
  categories with real captions, and training data whose licences allow commercial
  use, which the current model cannot offer.
- Run the in-browser model on WebGPU where the browser supports it.
- Photometric refinement: derive surface normals and materials from shading rather
  than silhouettes alone.
- Parametric reconstruction — fit primitives and constraints to the mesh to produce
  genuinely editable CAD rather than a faceted B-rep.
- Multi-view diffusion for stronger cross-view identity.
- Distributed job queue (Redis/Celery) for multi-instance deployment.
